# v0.3.0 开发记录：从 Agent 基座到可演示 MVP

本文记录 GitHub 原有 Agent 基座提交 `6258feb` 到发布 tag `v0.3.0`（`127cf65`）之间的演进。目标是帮助后续学习、答辩和代码复习：不仅说明“改了什么”，也说明“为什么这样分层”。

> 凭据纪律：文中只出现环境变量名称，不包含 API Key、服务令牌、数据库密码或任何本地连接信息。

## 发布版本边界

- 发布 tag：`v0.3.0`，annotated tag，指向 `127cf65`。
- 发布内容：Legal QA、Contract Review、独立 AI-Service、LangGraph、DeepSeek 接入、核心法规/RAG、持久化 Chroma、前后端 Demo 与测试文档。
- OCR 边界：当前 MVP 只处理可提取文本的 PDF / DOCX / UTF-8 TXT；扫描件和图片合同返回明确业务错误，不进入 Agent。
- 发布后文档：本文会以独立的 `docs: add v0.3.0 development history` 提交进入 main，**不会移动** `v0.3.0` tag。

## 最终架构

```text
Frontend
    ↓
Backend（鉴权、文件、异步任务、事务、业务持久化）
    ↓ AiServiceClient
AI-Service
    ↓ AgentService → AgentRuntime → AgentRegistry
LegalQaAgent / ContractReviewAgent
    ↓ LangGraph Workflow
LangChain / DeepSeek / Tool
    ↓ Backend Internal API / Chroma / RiskRule
Backend 持久化（回答、引用、风险点、PDF 报告）
    ↓
Frontend 展示与轮询
```

其中 `BaseAgent → Registry → Runtime → Service → API` 分别解决：统一异步 Agent 契约、按 code 注册、运行时选择 Agent、服务层编排调用、HTTP 通用入口。Runtime 只决定“调用谁”，LangGraph 决定“该 Agent 内部如何执行”，LangChain 负责模型、Prompt、结构化输出和 Tool 能力。

## 逐 Commit 开发记录

### 1. `a6a2d6e feat(qa): add legal qa agent`

**问题与背景**：最初 Backend 的 QA 流水线只有基础问答处理，缺少可明确描述、可测试的法律问答业务实现。

**主要代码与作用**：新增 `backend/app/slices/qa/agent.py` 中的早期 `LegalQaAgent`，由它组合问题、法规候选、回答和引用；`qa/pipeline.py` 改为调用该 Agent，`test_qa.py` 覆盖回答和引用落库。前端 `api/qa.ts` 适配异步消息返回的预分配 assistant message id。

**完成与架构意义**：形成了最初的 `Backend → Backend LegalQaAgent` 纵切面，先验证“回答 + citation 持久化”业务语义。它是后续迁移来源，而不是最终 Agent 所在位置。

**验证**：提交包含 QA 测试更新；后续完整 Backend pytest 覆盖了这条持久化语义。

### 2. `6c3d934 feat(review): add contract review agent`

**问题与背景**：合同审查流水线此前将风险分析细节直接放在 Pipeline 中，不利于把“合同审查”作为可独立演进的业务能力。

**主要代码与作用**：新增早期 `backend/app/slices/review/agent.py`，提取条款、规则、法规依据和风险点；Review Pipeline 改为消费结构化审查结果。

**完成与架构意义**：形成最初 `Backend → ContractReviewAgent → 风险点/报告持久化` 的闭环，并为后续七节点 Graph 明确了业务步骤。

**验证**：提交同步更新 Review Pipeline；后续 Review pytest 与真实合同审查联调验证了持久化和报告结果。

### 3. `21dda55 fix(agent): resolve lint issues`

**问题与背景**：早期两条 Agent 纵切面引入后，需要先保证项目代码风格和静态检查不因新实现退化。

**主要代码与作用**：清理 Agent 相关 lint 问题，不改变业务契约。

**完成与架构意义**：让后续大规模迁移有稳定的静态检查基线，避免把格式/未使用导入等噪声混入架构问题。

**验证**：ruff 通过；此提交没有引入新的业务行为。

### 4. `25737f9 refactor(qa): route legal qa through ai-service`

**问题与背景**：正式 Agent 若继续放在 Backend，会使数据库、会话持久化与模型/Graph 强耦合，且 AI 能力无法独立部署和测试。

**主要代码与作用**：

- AI-Service：BaseAgent 改为 `async invoke(input, context)`；增加 `AgentContext`、`LegalQaInput`、`LegalQaResult`、`LegalQaState`。
- `LegalQaAgent` 保持薄入口；`LegalQaGraph` 固定为 `prepare_query → retrieve_law → generate_answer → validate_citations → finalize`；Node、Prompt、State 分文件管理。
- `LawRetrievalTool → BackendClient → Backend Internal API` 代替 Node 中直写 HTTP；Fake Tool/Client 支持离线测试。
- Backend：`AiServiceClient` 调用通用 `POST /api/v1/agent/invoke`；QA Pipeline 只负责消息、引用、失败语义和事务；删除旧 Backend LegalQaAgent 正式副本。

**完成与架构意义**：调用链从 `Backend → Backend LegalQaAgent` 变为：

```text
Backend → AiServiceClient → AI-Service → Runtime → Registry
→ LegalQaAgent → LegalQaGraph → LawRetrievalTool
→ Backend Internal API → KB → LegalQaResult → Backend 持久化
```

Backend 不再理解 LangGraph 细节，Agent 也不直接访问业务数据库。`request_id` / `trace_id` 和 `AgentContext` 则让一次调用可跨服务追踪。

**验证**：新增 Runtime、Registry、AgentNotFound、Graph、Tool、Adapter 正常/超时/非 2xx/schema 错误测试；后续真实 DeepSeek 与 QA 端到端联调通过。

### 5. `2ab2a20 refactor(review): route contract review through ai-service`

**问题与背景**：Legal QA 已归位后，合同审查仍有一套 Backend 内嵌 Agent，会造成两种正式 Agent 架构并存。

**主要代码与作用**：

- 新增 `contract_review/{agent,state,graph,nodes,prompts}.py`，注册 `contract_review`。
- `ContractReviewGraph` 固定七节点：`prepare_contract → extract_terms → retrieve_laws → retrieve_risk_rules → analyze_risks → validate_sources → finalize`。
- `BackendClient` 增加风险规则 Tool；Backend Internal API 只暴露 Agent 真正需要的法规和风险规则数据。
- Review Pipeline 改用 `AiServiceClient.contract_review`，保留 Backend 的任务状态、RiskPoint、Report 持久化；删除旧 Backend ContractReviewAgent。

**完成与架构意义**：两个正式 Agent 统一进入 AI-Service。`validate_sources` 约束风险点的来源类型，无法验证的输出会降级为 `llm_inference`，避免把模型臆测伪装成法规依据。

**验证**：补充 ContractReview Graph、Tool、Adapter 和 Pipeline 测试；之后真实 TXT 合同联调成功生成风险点和 PDF 报告。

### 6. `d995f9e feat(ai): integrate deepseek langchain provider`

**问题与背景**：Fake/Stub 适合自动化测试，但无法验证真实模型在正式 Agent 结构化输出中的表现。

**主要代码与作用**：在 `ai-service/app/llm/deepseek.py` 集中以 LangChain `ChatOpenAI` 接入 OpenAI-compatible DeepSeek API；配置仅从 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL` 读取。Agent Node 通过依赖注入使用该模型，异常转换为稳定的 AI 调用错误。

**完成与架构意义**：真实 LLM 仍只有一个封装点，业务 Node 不散落厂商 SDK 调用；没有密钥时测试继续使用 Fake/Stub，因此 CI 不依赖外网。

**验证**：新增 DeepSeek Provider 单元测试；随后实际完成 Legal QA Graph 的真实模型 smoke test。

### 7. `2e8c6de feat(kb): add core legal seed corpus`

**问题与背景**：RAG 只有流程没有可重复导入的基础法规/规则，演示和测试无法保证检索输入一致。

**主要代码与作用**：新增受版本控制的 `core_legal_corpus.json`，包含首批核心法规和风险规则；`import_core_legal_corpus.py` 使用内容哈希/规则 code 实现幂等导入；工具 README 说明运行方式。

**完成与架构意义**：将“需要什么法律知识”变成可审查、可复现的项目资产，而不是本地人工录入状态。

**验证**：导入脚本与初版语料测试加入 Backend 测试集。

### 8. `17088ed feat(kb): integrate persistent chroma vector store`

**问题与背景**：内存向量后端进程重启即丢失，无法形成可演示的 RAG 索引生命周期。

**主要代码与作用**：`infra/vector.py` 增加 Chroma `PersistentClient`、collection 管理、按 document 删除后 upsert、检索与异常转换；KB 索引和查询改为在线程中调用向量能力。

**完成与架构意义**：实现语料分块 → embedding → Chroma 持久化 → 重启后检索的完整存储链。当前 embedding 是确定性开发实现，Chroma 持久化不等于已接入生产级语义 Embedding Provider。

**验证**：新增 Chroma 持久化与检索测试；本地实际导入核心语料并验证检索命中。

### 9. `f45fbac refactor(review): limit mvp to text-extractable contracts`

**问题与背景**：OCR 尚未接入时，扫描 PDF/图片若被送入 Agent，会产生空文本、难解释的失败或假结论。

**主要代码与作用**：解析层支持 UTF-8 TXT；审查入口限定 PDF/DOCX/TXT；Review Pipeline 在 `text_extract` 阶段检测空文本，返回“当前版本暂不支持扫描件 OCR”的明确业务错误；前端上传提示同步调整。

**完成与架构意义**：合同 Agent 的输入契约收敛为 `plain_text`。未来可在同一分流点补 OCR Provider，而无需让 Graph 处理文件二进制或 OCR 状态。

**验证**：文件解析、上传限制和 Review 失败语义测试更新。

### 10. `526f57b test(kb): verify core corpus import idempotency`

**问题与背景**：语料导入工具若重复执行导致重复法规或规则，检索结果和演示会随运行次数变化。

**验证**：核心语料幂等测试通过。

### 11. `92c9efd fix(ai): support deepseek json mode for review`

**问题与背景**：真实 Contract Review 使用默认 structured output 方式时，DeepSeek Chat Completions 对 JSON Schema 的兼容性不足，导致结构化审查失败。

## v0.3.0 相比 GitHub 原始基座新增内容

### Backend

- `AiServiceClient` 将 QA/Review Pipeline 与 Agent 内部实现解耦。
- Internal API 通过 `X-Internal-Service-Token` 暴露最小法规/风险规则数据面。
- Backend 持续负责鉴权、幂等、BackgroundTasks、事务、回答/引用/RiskPoint/PDF 报告持久化。

### AI-Service

- BaseAgent 异步契约、Registry、Runtime、Service、通用 Agent API。
- `legal_qa` 和 `contract_review` 两个正式注册项；DemoAgent 与 AgentNotFound 语义保留。
- State/Graph/Node/Prompt/Tool 分层，避免单个 Agent 文件膨胀。

### Legal QA

- `LegalQaState` 管理问题、来源、答案；Graph 依次准备问题、检索法规、生成、校验引用、收尾。
- Citation Validation 只接受可映射的来源，再由 Backend 落库。

### Contract Review

- 七节点 Graph 把条款提取、法规检索、风险规则、风险分析和来源校验拆开。
- Agent 只接收 `plain_text`；Backend 解析文件并产生异步任务、风险点和报告。

### RAG / Chroma

- 版本化核心法规和风险规则、幂等导入工具、分块索引。
- Chroma PersistentClient 支持索引重建和重启后检索；当前 Embedding Provider 仍是开发实现。

### DeepSeek

- LangChain `ChatOpenAI` 通过 OpenAI-compatible 接口封装真实调用。
- Legal QA 使用文本生成；合同审查使用 JSON mode 结构化输出，并处理 `LLM_UNAVAILABLE` 等稳定错误。

### Frontend

- QA 会话/消息轮询、引用展示；合同上传、任务进度、风险点、报告下载。
- 前端只依赖 Backend API，不直接耦合 Agent Graph。

### Testing 与文档

- Fake LLM/Fake Vector/Fake Backend Client 保障测试不依赖真实网络。
- 增加 Registry/Runtime/Graph/Tool/Adapter、语料幂等、持久化 Chroma、Pipeline 和失败语义测试。
- README、MVP Demo 指南与本文共同覆盖架构、环境变量、启动、测试、Demo 和限制。
