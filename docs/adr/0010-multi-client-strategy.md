# 多端策略：三端共用同一套 REST API，各自独立开发，不引入跨端框架

## 背景与决策

需求提出移动端要"先以网页为主，后面移植小程序和安卓 APP"。而全部既有文档中关于移动端**只有一句话**（需求说明书 §2.3"移动端为辅助"），既无路线图也无设计。

**决策**：

1. **三端共用同一套 REST 接口**（`/api/v1`）。**不引入 uni-app / Taro 等跨端框架**，三端前端各自独立开发。
2. **交付顺序：Web（P1）→ 微信小程序（P5）→ 安卓 App（P6）**。
3. **不做 iOS**（团队无设备，明确放弃）。
4. **鉴权设计维持不变**（访问令牌走 `Authorization` 头、刷新令牌走请求体）——该设计天然对三端成立，见下"后果"。
5. 一期内**不实现任何移动端代码**，但必须确保接口契约对三端成立（见 03-概要设计《多端路线与一期的约束》）。

## 理由

### 1. 为什么不引入跨端框架

**(a) 三者不共用代码库，是收益而非损失。**
小程序**不能直接运行 Vue 3 Web 代码**——它没有 DOM，用 WXML/WXSS；安卓用原生或 Kotlin。跨端框架的"一套代码编多端"确实存在，但代价是：

- Web 端**不能使用浏览器专属库**。而我们的 Web 端依赖 Element Plus、TinyMCE/Quill（合同在线编辑）、Signature Pad（手写签名图片）——这些**在跨端框架下都用不了**，等于 Web 端要重写界面。**这是最硬的一条**：Web 是本项目的主战场，为了迁就小程序而削弱它，方向反了。
- 在 4 人、4–6 周的最紧时期引入一个陌生框架，调试与踩坑成本不可控。
- 跨端框架对**富文本编辑、手写签名、文件上传**这些本项目的关键交互支持最弱，恰好都在我们需要的功能上。

**(b) REST 接口本来就是三端通用的。**
REST + JSON 是跨客户端最成熟的方案。三端各自做界面、共用一份契约，是移动端的标准做法，不需要框架来"粘合"。

**(c) 团队背景支持独立开发。**
四名成员均做过小程序或安卓方向（已确认），因此"各自独立开发"不构成学习成本风险。

### 2. 为什么小程序排在安卓之前

**外部依赖要尽早暴露。** 微信小程序有**两项我们无法控制的前置条件**：

| 前置条件 | 说明 |
| --- | --- |
| **ICP 备案的域名** | 微信要求后端域名经备案并在公众平台**配置服务器域名白名单** |
| **HTTPS** | 小程序强制 HTTPS，且证书需受信任 |

这两项**不是靠努力能解决的**——若拖到最后才发现域名通不过微信校验，安卓做完也白做。反之，安卓晚做**没有任何外部风险**。
此外，小程序所需的后端能力（HTTPS + 域名白名单 + 无 Cookie 鉴权）是安卓所需能力的**超集**，先做小程序等于为安卓把路铺平。

### 3. 为什么不排成"两个并列 P5"

4 人同时开两个新端，且都不是一期核心，会同时拖慢两条线。串行推进能保证每一端都真正做完。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| **uni-app / Taro 跨端框架** | Web 端将失去 Element Plus、TinyMCE、Signature Pad 等浏览器专属库（本项目关键交互），等于重写界面；且在周期最紧时引入陌生框架 |
| **P5 安卓 → P6 小程序** | 微信域名校验与备案是外部依赖，拖后会成为永久悬空项 |
| **小程序与安卓并列 P5** | 4 人同时开两个新端，两条线都被拖慢 |
| **WebView 套壳（把 Web 页面包成 App）** | 微信小程序**明确禁止**通过 WebView 加载外站内容，该路径在小程序上不成立 |
| **做 iOS** | 团队无设备、无能力、无动力，明确放弃 |

## 后果

### 一条"无意的正确"，现转为有意决定

[05-接口设计](../05-接口设计.md) §4.1 冻结的鉴权方案是：**访问令牌走 `Authorization: Bearer` 头，刷新令牌走请求体**。当时是**无意中**选对的，但事后验证：**该设计对浏览器、小程序、原生 App 三者均成立**。

其真正的替代方案是**把刷新令牌放进 `HttpOnly` Cookie**（Web 端更安全）。但**小程序与原生 App 不使用浏览器 Cookie 机制**，该方案会迫使后端维护**两套鉴权逻辑**。因此维持现方案，并在《05》中补记为**有意的多端决定**。

### 一期必须为多端做对的事（否则 P5/P6 需要返工）

| 必须做对 | 原因 |
| --- | --- |
| 接口**不对任何客户端做特殊处理** | 不做 User-Agent 嗅探、不为 Web 加"只有浏览器能用"的字段。三端看到同一份契约 |
| **响应体与错误码不含 Web 专有语义** | 例如不返回 HTML、不依赖浏览器行为、不把 `302` 重定向当作业务语义 |
| **分页与异步约定对小程序可用** | 小程序对长连接支持有限，因此"创建 + 轮询"是其最稳的异步模式——我们的设计恰好如此 |
| **文件上传保持 `multipart/form-data`** | 小程序用 `wx.uploadFile`、安卓用 OkHttp，均支持该格式；若改成 Base64 内嵌则三端都要额外处理 |

### 对后续文档的约束

- Web 端**可以自由使用浏览器专属库**，但**不得把浏览器行为写进接口契约**（如依赖 Cookie 自动携带、依赖 `Referer` 判断来源）。
- 生产域名必须是 **HTTPS 且经 ICP 备案**（小程序的硬性要求），这一项需在 P2 部署阶段确认，**不能拖到 P5**。
- 三端各自的**错误提示文案**由各端自行处理，后端只提供 `code` 与中性的 `message`。
