# 采用 monorepo 与「纵切面 + 把关人」协作模型

## 背景与决策

四名开发者需要各自完整经历一遍「需求—设计—开发—测试—部署」的项目周期，同时只能交付**一套**可运行代码。我们否决了「每人一条长分支、最后择优融合」（字面上最符合"人人做完整项目"，但最终只有一人的成果被采用，其余三人工作量归零，且四条独立分支的合并是架构级冲突而非文件级冲突），改用：

- **代码组织**：单仓库（monorepo），`backend/`（FastAPI）、`frontend/`（Vue 3）、`contracts/`（Solidity）、`deploy/`、`docs/` 同仓共存。
- **分工方式**：按**纵切面**（一条端到端业务链路）认领，覆盖数据→后端→AI→前端→测试→部署，使每人经历完整周期；跨切面的公共层（认证、文件存储、错误码、日志、区块链/签章封装）共同设计、由基座负责人率先落地。
- **协作流程**：需求拆为 GitHub Issue → 任何成员可开分支提 PR → 模块**把关人**评审；**把关人持 2 票、其他成员各 1 票**（总票重 5，不会平票）；**弃权计为反对**。
- **裁决边界**：代码缺陷、安全漏洞、违反契约或破坏分层依赖 —— 属**技术缺陷**，由把关人**直接驳回**，不走投票；两种实现均合法的**方案分歧**才走投票。被否决的方案及其原因记入 ADR 或 PR 讨论，作为过程性证据。
- **契约变更**：不设正式变更登记流程。变更须在团队内知会，并在 PR 描述中说明影响范围。

## 被否决的替代方案

- **每人独立完整实现一遍（四套代码，择优交付）**：重复劳动占比过高；最终仍只交一套，`git` 历史无法体现其余三人的真实工作；答辩时无法证明分工。
- **按技术分层分工（一人后端、一人前端、一人 AI、一人测试）**：看似清晰，实则使每人只接触单一技术层，与"完整项目周期"的目标背道而驰。
- **共同所有、无把关人**：4 人 4 票，一旦 2:2 死锁且无裁决人；质量责任无唯一姓名可追溯。

## 后果

- 仓库根目录为 `law-wiz/`，`docs/`、`backend/`、`frontend/`、`contracts/`、`deploy/` 同仓共存。
- 把关人是**裁决者而非唯一实现者**，因此任何模块都允许非主导成员提交 PR。
- 投票规则要求 PR 评审**必须在合并前完成**，不接受"先合并后补评审"。
- 项目管理分工：GitHub Issues 承载"每个功能点的实现与 PR 流转"，禅道（ZenTao）承载"里程碑、任务分解与缺陷"，**两者不重复录入同一批数据**。
- 凭据（面板密码、禅道密码、SSH 私钥、第三方服务密钥）不写入仓库，一律存放于团队内部凭据管理，本地使用被忽略的 `.env` 文件。
