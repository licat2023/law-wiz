# 向量存储抽象为接口，保留 Chroma 但预留 pgvector / Milvus 替换点

## 背景与决策

有人提出将 MySQL 与向量数据库统一到 PostgreSQL（`pgvector`），以减少需要维护的数据库种类。

**决策**：**保留**技术栈已确认的 MySQL 8 + Chroma 组合，但在概要设计中把向量存储抽象为 `VectorStore` 接口（写入、检索、删除、按元数据过滤），业务代码只依赖该接口，不直接依赖 Chroma 客户端。`pgvector` / Milvus 作为该接口的备选实现。

## 理由

1. **收益小于预期**：Chroma 的单机模式本质是「SQLite + 进程内向量索引」，并非一个需要独立运维的数据库服务；"少维护一个数据库"的实际收益有限。而技术栈文档已明确"所有选型均已确认为最终方案，避免多选并列带来的实现分歧"，改动会破坏团队自定的规则。
2. **一期不存在性能压力**：一期语料规模为 1–3 MB 文本（约 1000–3000 个向量块），`pgvector` 与 Chroma 均远超所需。`pgvector` 的性能劣势（索引构建与检索延迟随向量规模上升而显著劣化）在该规模下不构成决策依据。
3. **保留选择权而不付出代价**：抽象接口的成本约为半天，而推翻已确认选型的成本是重做数据层设计与重新评估。接口化让"以后想换"变成一个局部改动。

## 被否决的替代方案

- **立刻迁移到 PostgreSQL + pgvector**：为一个不存在的问题付出重构成本，并违反已冻结的技术栈决策。
- **不做抽象，直接调用 Chroma 客户端**：使未来的替换成本从"换一个实现类"上升为"全仓搜索替换 + 重测"。

## 后果

- 数据层设计中，**向量本体存放于外部向量存储**，MySQL 只保存知识库文档的元数据（来源、法条号、标题、生效日期、版本）与**外部向量 ID 的映射**。因此更换向量实现时，关系型数据无需迁移。
- 若后期确需迁移，触发条件为：向量规模超出单机内存、需要与业务数据强一致的事务、或需要多租户隔离。届时新开一条 ADR 记录迁移决策。
