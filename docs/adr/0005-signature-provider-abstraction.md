# 签章能力做通道抽象；可靠电子签名由第三方签章服务承担，平台只做编排

## 背景与决策

需求提出"让双方在本平台签署合同，且签署具有法律效力"，并探讨过"平台自己生成唯一电子签名"与"接入国家网络身份认证"两条路径。

**决策**：
1. 签章能力抽象为**通道接口**（`SignatureProvider`），包含：创建签署任务、查询签署状态、定位签署位置、验签。
2. **默认实现为第三方电子签章服务（开发者版）**，由它承担**可靠电子签名**的法律效力；本平台**不自行签发证书**。
3. **开源实现（`pyHanko` + 自建 CA）作为后期可选通道**，用于离线演示与零成本开发，但**对外表述中不得声称其具备与手写签名同等的法律效力**。

## 理由

1. **国家网络身份认证公共服务不可接入**：该服务面向具备资质的接入机构，需单位资质、商务协议与安全评估，个人与课程项目无法申请。且它解决的是**身份核验**，不提供**电子签名**能力 —— 核验"你是谁"与"由谁签发你的签名证书"在《电子签名法》下是两件事。
2. **平台自建 CA 无法主张完整法律效力**：《电子签名法》第十三条要求可靠电子签名同时满足四项条件，其中"签署时电子签名制作数据仅由签名人控制"与身份可识别性，依赖**受信任的证书链**。自签根证书不在任何受信根列表中，因此自建 PKI 只能证明「文档未被篡改」与「签名时刻存在」，**不能证明「签名人身份」**。
3. **通道抽象的必要性**：签章服务商接口差异大、开发者版有额度与可用性限制。绑定单一服务商会使演示与开发受制于外部配额，而抽象成本仅为一个接口。

## 被否决的替代方案

- **直接在业务代码中调用某一家签章服务 SDK**：可用性受制于该服务商，替换成本高。
- **仅用自建 PKI，宣称具备法律效力**：属于无法成立的自我声明，在答辩与真实使用中均站不住。
- **用手写签名图片（`SignaturePad` 生成）作为电子签名**：签名图片是可被复制粘贴的位图，不满足"制作数据专属于签名人"的条件，**不是**《电子签名法》意义上的电子签名。本平台允许使用签名图片用于视觉呈现，但对外表述中必须与电子签名区分（见 `CONTEXT.md`）。

## 后果

- `01-需求说明书` §3.7 中"可靠的电子合同与纸质合同在法律上具有同等效力"一句必须改写为：**通过具备资质的第三方电子签章服务提供可靠的电子签名，依据《电子签名法》第十四条与手写签名或盖章具有同等法律效力**。效力来源是第三方 CA 证书，而非平台自身。
- 前端与文档中出现"手写签名"时，一律称**签名图片**，不得简称"电子签名"。
- 国家网络身份认证在《可扩展性》一节记为"后期可选身份核验通道，接入需机构资质，本期不实现"。
