# 分期交付：一期只做 M2 合同智能审查与 M3 法律 AI 问答

> **状态：已修订**（2026-09-13 增补 P5 微信小程序与 P6 安卓 App 两期，见 [ADR-0010](0010-multi-client-strategy.md)；**一期范围修正为 M1+M2+M3，见 [ADR-0011](0011-p1-scope-includes-m1.md)**）。下文"一期 = M2+M3"是最初的表述，**已由 ADR-0011 修正**。

## 背景与决策

需求说明书规划了 M1–M7 共 7 个模块（含区块链存证、电子签章、印章管理三条重技术栈），而约束条件是 **4 名开发者、4–6 周**。经评估，在周期内完成全部 7 个模块不可行。

**决策**：设计完整保留 M1–M7，实现按**六期**分批交付（P1–P4 为功能模块范围，P5–P6 为客户端移植）：

| 分期 | 范围 | 目的 |
| --- | --- | --- |
| **P1 一期** | **M2 合同智能审查 + M3 法律 AI 问答** | 交付可运行、可演示的 AI 核心链路，构成课业的最小可交付成果 |
| **P2 二期** | 部署运维（Docker Compose / Nginx / CI）+ **M4 区块链证据存证**最小闭环（文件→SHA-256→可信时间戳→上链→验证查询） | 补齐工程化能力，落地第二条技术栈 |
| **P3 三期** | **M6 电子合同生成与签署**（模板起草、AI 起草、在线编辑、签署、归档）+ **M7 电子印章与签名管理**（印章制作、实名认证、用印） | 形成「起草→签署→存证→验证」业务闭环 |
| **P4 四期** | 多方签署模式、合同到期提醒、印章分级授权、停用销毁、权限配置、安全审计、异常用印预警 | 合规与管控增强，可在不影响演示的前提下延后 |
| **P5 五期** | **微信小程序端** | 移动端移植，见 [ADR-0010](0010-multi-client-strategy.md) |
| **P6 六期** | **安卓 App** | 移动端移植，见 [ADR-0010](0010-multi-client-strategy.md) |

## 理由

1. **一期即可提交**：M2+M3 共用同一套「Chroma 知识库 + LangChain + LLM」底座，边际成本低，且两者合起来构成一个完整的"AI 法律助手"能力面，足以支撑课业交付与答辩。
2. **依赖顺序驱动分期**：M6 必须在 M4 能存证、M7 能盖章之后才有法律闭环；先做 M4 再补 M6 的顺序不可颠倒。
3. **避免"设计庞大但只做两成"的评审风险**：每份设计文档均在功能点级别标注**本期收录／后期收录**，并单列《交付边界与分期》一节，将范围管理显式化，而非事后解释。

## 被否决的替代方案

- **砍需求，把 M5/M6/M7 从需求说明书中删除**：会使已完成的 M6/M7 需求内容（含 2025 年《电子印章管理办法》法律依据、业务流程图）全部作废，且"设计完整、分期交付"在评审中优于"需求缩水"。
- **不砍范围，全部并列实现**：4–6 周内必然全面延期，最终无可演示产物。

## 后果

- M4/M6/M7 相关设计在文档中**完整保留**，但代码实现延后；文档与代码之间会存在**阶段性不一致**，这是预期状态。
- 团队分工以一期（M2+M3）为基准编排，其余成员在二期起转入 M4/M6/M7。
