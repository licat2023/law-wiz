# 密码算法主链路采用 RSA-2048 + SHA-256，国密 SM 系列列为扩展点

## 背景与决策

需求说明书 §3.8 要求遵循 **GB/T 38540-2020《信息安全技术 安全电子签章密码技术规范》**（国密标准），而技术栈文档仅含糊地写了"hashlib / 国密算法库"。二者之间存在未解决的口径冲突。

**决策**：密码算法主链路采用 **RSA-2048 + SHA-256**；**SM2/SM3 列为后期扩展点**，不在本期实现。同时，需求说明书中关于国密合规的表述调整为**合规边界声明**（见下）。

## 理由

1. **工程成熟度差距显著**：RSA/SHA-256 链路在 Python 生态（`cryptography`、`pyHanko`、`PyJWT`）中是一等公民，文档、示例、排错资料完备；SM2/SM3 的 Python 侧可用实现（如 `GmSSL` 绑定）在工程成熟度与资料完备性上存在明显差距，会为一期引入不必要的集成风险。
2. **合规声明与合规能力是两件事**：GB/T 38540-2020 的合规性依赖**经商用密码产品认证的密码模块**，而非"使用了国密算法"。课程项目即使全部改用 SM2/SM3，也不构成对该标准的合规。因此，在一期宣称"遵循 GB/T 38540-2020"属于**过度自我声明**，风险高于收益。
3. **一期不涉及签章**：一期范围（M2/M3）只需 SHA-256 用于文件哈希与语料指纹，密码算法的主要战场在 P3，届时仍有充分时间重新评估。

## 被否决的替代方案

- **一期即以 SM2/SM3 为主链路**：为一期引入非必要的集成风险，且并不能换来真实合规性。
- **双算法并行、运行期可切换**：在没有真实合规需求驱动的情况下，属于过度设计，增加测试矩阵而不解决任何当下问题。

## 后果

- 全平台统一使用 **SHA-256** 计算文件哈希与知识库文档指纹（`CONTEXT.md` 已将其写入术语定义）。
- 需求说明书中的"遵循 GB/T 38540-2020"已改写为**合规边界声明**：明确"设计参照该标准的安全目标，通过第三方签章服务提供可靠电子签名能力，自建国密签章为后期扩展点"；技术栈文档中的"hashlib / 国密算法库"已改为 `cryptography` 并注明国密延后。落点：01 §2.3 合规边界声明、§3.8 输入输出要求；02 §3.3、§4.2。
- 若后期确需国密，改动被限制在**密码算法适配层**内，不触及业务逻辑。
