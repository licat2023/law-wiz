# 一期范围修正：P1 = M1 + M2 + M3

> **状态：已接受**。本 ADR **修正** [ADR-0002](0002-phased-delivery-ai-first.md) 对一期范围的表述，**不修改其原文**。

## 背景

ADR-0002 的标题与决策表把一期写为「只做 M2 合同智能审查 + M3 法律 AI 问答」。但 M2 与 M3 的**全部业务接口都在鉴权之后**：

- 审查任务与文件记录都带 `user_id` 外键，归属到 `user` 主体；
- 双令牌鉴权是 `/api/v1` 下除 `/health` 外每个接口的前置；
- 15 张表中 6 张以 `user` 为外键目标。

因此 M1（用户管理）不是"可选的前置"，而是一期**无法绕开**的组成部分。

《01-需求说明书》§5.3 与《03-概要设计》§3.3 均已按 **M1 + M2 + M3** 表述，与 ADR-0002 的「M2 + M3」不一致；根目录 README 的分期表同样写 M1+M2+M3。

## 决策

**一期（P1）范围为 M1 + M2 + M3，共 15 个功能点。**

| 模块 | 功能点 | 数量 |
| --- | --- | --- |
| M1 用户管理 | M1-01 ~ M1-03 | 3 |
| M2 合同智能审查 | M2-01 ~ M2-07 | 7 |
| M3 法律 AI 问答 | M3-01 ~ M3-05 | 5 |

**AI 核心链路（M2 + M3，共 12 个功能点）仍是一期的交付重点**；M1 是其**必要前置**，而非与之并列的交付目标。

## 理由

1. **M1 是被依赖项**：没有已认证的用户主体，审查任务、文件与问答会话都无处归属。
2. **ADR-0002 的实质取舍未变**：它要表达的是"一期集中交付 AI 核心链路，把区块链与签章留到后期"。收录 M1 与这一取舍并不冲突 —— **被修正的是表述的完备性，不是分期的选择**。
3. **M1 已实现**：`auth` 纵切面已作为端到端参考实现落地。把它排除在一期之外，会使已完成的工作在一期范围里失去归属。

## 被否决的替代方案

- **直接改写 ADR-0002 的原文**：ADR 记录的是"在当时的认识下为什么这样决定"。事后静默改写会让读者**无法分辨哪一版是最初的判断**，决策记录因此失去可信度。正确做法是保留原文、另立 ADR 修正，使"范围如何演变"本身成为可追溯的证据。
- **把 M1 另立为"P0 基座"**：会引入 ADR-0002 未定义的第七个期次，使已经冻结的"六期"交付口径失效，且与 03 §3.3 的分期表冲突。

## 后果

- 《01-需求说明书》§5.3、《03-概要设计》§3.3 与根目录 README 的分期表**无需改动**，本 ADR 与它们一致。
- ADR-0002 的**标题与决策表不再代表现行范围**；其状态行已增补指向本 ADR 的注记，原文保持不变。
- 一期的 GitHub Milestone 与 Issue 按 M1 + M2 + M3（15 个功能点）建立。
