# 一期不建能力抽象层，外部能力由切片直接接入

> **状态：已接受**。本 ADR **修订** 03 §2.4 / §2.5、05 §7 与架构图第 ⑤ 层中
> 对能力抽象层的**强制性**要求。

## 背景

原设计规定：**业务服务层不得直接调用外部厂商 SDK，所有外部调用必须经能力抽象层**
（03 §2.4、05 §7、架构图第 ⑤ 层）。该层定义 8 个 Provider 接口 ——
`LLMProvider` / `EmbeddingProvider` / `OcrProvider` / `VectorStore` / `FileStore` /
`ChainProvider` / `SignatureProvider` / `TimestampProvider`，一期需要前 5 个。

而约束条件是 **4 名开发者、一期 4–6 周**，且一期**每种能力只需要一个实现**。

## 决策

**一期不建 Provider 接口体系。** 外部能力由需要它的切片**直接接入**：

| 能力 | 接入方 |
| --- | --- |
| 合同文件存储（MinIO） | `files` 切片（B） |
| 云端 OCR API | `files` 切片（B） |
| DeepSeek LLM | `review` / `qa` 切片（B / C） |
| 嵌入与 Chroma 向量检索 | `knowledge` / `qa` 切片（C） |

**保留一条约束**（它不是抽象，是"别散落"）：**同一个外部能力只在一处封装**，
其它地方复用那个封装。避免同一个 SDK 在五个文件里各写一遍 —— 那才是真正让后续替换变贵的写法。

## 理由

1. **接口的形状只能由第二个实现决定，不能由猜决定。** 现在只有 DeepSeek 一个 LLM 实现，
   照着它抽出来的接口，等真要接 Ollama 时大概率要重画。**晚抽象比早抽象便宜。**
2. **它是一期的串行阻塞点。** 抽象层不落地，B 与 C 一行 AI / OCR / 存储调用都写不了。
   为一个 4 人 4 周的项目先造"先于业务存在的公共层"，等于把可并行的工作变成串行。
3. **一期没有替换需求。** 8 个接口中 `ChainProvider` / `SignatureProvider` /
   `TimestampProvider` 属 P2/P3，一期用不到；其余 5 个各自只有一个实现。

## 被否决的替代方案

- **照原设计先建 8 个 Provider 接口 + memory 实现 + 依赖注入**：这正是本 ADR 要改掉的做法。
  代价是数天工时、一整套为"将来可能替换"服务的代码，以及**全队等它完成才能开工**。
- **完全不设收敛点，各处直接 `import` 厂商 SDK**：短期最快，但同一 SDK 会在多处出现，
  真需要替换时要全仓库搜。因此保留上面那条"同一能力只在一处封装"。

## 后果

- 03 §2.4 的"必须经能力抽象层"改为"一期直接接入，同一能力只在一处封装"；
  03 §2.5 与架构图第 ⑤ 层改名为**外部能力接入**；05 §7 的接口清单降级为**演进方向**，
  不再是本期的实现要求。
- **03 §7.2 的否决边界必须同步调整**：原先把"破坏分层依赖"列为可由把关人直接驳回的技术缺陷。
  若不改，团队按本 ADR 写出的代码会被自家规则判为缺陷 ——
  **这是本 ADR 必须同时改文档、而不只是改代码的原因**。
- 演进方向仍保留：当某个能力**真的出现第二种实现**时（LLM 接 Ollama、向量库换 pgvector、
  本地 OCR 替代云端），在那一刻抽接口 —— 那时接口形状是已知的。
