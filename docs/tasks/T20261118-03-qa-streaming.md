# 法律问答流式输出

## 用户需求依据

- R1，本次聊天，用户在法律问答与报告选择交付后要求“改流式输出”。

## 当前任务理解

普通法律问答、整份报告追问和风险项追问在模型生成正文时逐段显示。最终回答、引用和生成错误按既有契约入库。刷新或断网时能重连正在生成的回答，或从会话历史取回最终结果。延续账号权限、请求幂等和既有会话接口。流式内容仅展示回答正文，不展示推理过程。

实施选择：保留异步提交，新增按助手消息订阅的 SSE 接口。AI 服务使用逐行 JSON 传输新文本和最终结果，业务后端暂存生成中的正文。只有通过校验的最终回答和引文写入会话。浏览器兼容旧后端的轮询入口。

## 实施方案

1. 验证当前模型客户端能返回增量内容，结构化答复的 `answer` 字段可逐步解析。新增 AI 流式接口，普通和报告模式复用检索及最终引用校验。
2. Java 异步任务转发增量，校验订阅账号和消息归属。后台继续生成，连接中断不重发提问，完成后从 MySQL 读取正式结果。
3. 前端边接收边显示，断线回到原有查询流程。验证普通问答、报告追问、重复订阅、失败、跨账号拒绝及代理转发。

## 验证结果与未解决事项

- 部署前最小验证已确认当前锁定版本能解析未结束的 JSON 字符串。以无业务数据的短消息调用真实生成模型，收到 17 段内容增量。
- 从 Git 暂存树导出干净源码。前端 ESLint、类型检查、生产构建及静态站点镜像构建通过。Java 21 Maven 构建和五项测试通过。AI 服务 Ruff 检查、格式检查及九项测试通过。模拟响应验证分段转义、忽略推理内容、正式引用编号和截断结果处理。
- 使用虚构问题通过生产版前端代理调用真实模型。该次普通问答收到 544 段正文，首段约 11.14 秒，结束约 13.12 秒。首段显示时数据库仍是空占位，结束后取得 854 字的正式回复。重新订阅能收到已有正文，断开其中一条连接后另一条继续，完成后订阅只返回结束事件。
- 浏览器验证普通问答至少出现两次预览变化后刷新。同一条消息恢复并最终显示，历史仅保存一组问答。阻断流连接后页面仍从历史取回正式回复。整份报告及风险项追问均先显示增量，再显示同一条保存的正式回复。
- 重放幂等键得到同一消息 ID。未登录和跨账号读取分别返回 `40101` 与 `40301`，尝试订阅用户消息返回 `40402`。本机开发环境已更新，原有八个容器均健康。
