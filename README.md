# 智法宝（law-wiz）—— AI 法律助手平台

> 以智能之法，护权利之宝。

面向中小企业和个人用户的一站式智能化法律服务平台，通过 OCR、大语言模型（LLM）、法律知识库、检索增强生成（RAG）与区块链存证等技术的整合，提供从「合同起草签署」到「合同风险审查」，再到「法律咨询问答」和「电子证据固化」的全链条解决方案。

## 核心痛点

- 中小企业法务资源匮乏，合同审查依赖人工，成本高、效率低；
- 普通用户获取法律咨询的门槛高、渠道少；
- 电子证据易篡改、易消亡，在诉讼中举证困难、采信率低；
- 传统合同签署线下流程繁琐，电子印章管理不规范，用印风险难以管控。

## 功能模块

| 编号 | 模块名称 | 功能描述 | 优先级 |
| --- | --- | --- | --- |
| M1 | 用户管理 | 注册、登录、个人信息管理 | 高 |
| M2 | 合同智能审查 | 合同上传、OCR 识别、AI 风险分析、报告生成 | 高 |
| M3 | 法律 AI 问答 | 对话式法律咨询、知识库检索 | 高 |
| M4 | 区块链证据存证 | 证据上传、哈希计算、时间戳、上链存证、验证查询 | 高 |
| M5 | 个人中心 | 历史记录查看、存证管理 | 中 |
| M6 | 电子合同生成与签署 | 合同模板管理、AI 起草、在线编辑、电子签署、归档存证、验签 | 高 |
| M7 | 电子印章与签名管理 | 印章 / 签名制作、实名认证、审批授权、用印管理、停用销毁、权限配置、安全审计 | 高 |

其中，**M6 电子合同签署 → M4 区块链存证 → M6 合同验签**，以及 **M7 电子印章 / 签名为 M6 提供法律效力支撑**，共同构成「合同起草 → 签署 → 存证 → 验证」的完整法律证据链条。

## 技术栈概览

- **前端**：Vue 3 + Vite + Element Plus
- **后端**：FastAPI（Python）
- **AI 能力**：DeepSeek API + LangChain + Chroma（RAG）；OCR 走**云端 API**（本地 OCR 需 1.2–2 GB 内存，服务器不部署，见 [02-技术栈](docs/02-技术栈.md) §3.9）
- **区块链**：FISCO BCOS + Solidity 智能合约 + Web3.py
- **电子签章**：第三方电子签章服务（开发者版）承担可靠电子签名效力，平台负责编排与存证（见 [ADR-0005](docs/adr/0005-signature-provider-abstraction.md)）
- **密码算法**：RSA-2048 + SHA-256 主链路，国密 SM 系列为后期扩展点（见 [ADR-0003](docs/adr/0003-crypto-rsa-first-sm-later.md)）
- **数据存储**：MySQL 9.7、MinIO、Redis、Chroma
- **部署运维**：Debian 13、Docker Compose、OpenResty（1Panel 自带，复用而不另起）、GitHub Actions；Prometheus/Grafana 与 ELK 为**后期可选**

> **合规边界**：本项目参照 GB/T 38540-2020 的安全目标进行设计，但**不构成对该标准的合规声明** —— 该标准的合规性依赖经商用密码产品认证的密码模块。可靠电子签名能力由具备资质的第三方签章服务提供。

## 交付分期

设计完整保留 M1–M7 全部模块，实现按六期分批交付（详见 [ADR-0002](docs/adr/0002-phased-delivery-ai-first.md) 与 [03-概要设计](docs/03-概要设计.md) §3.3）：

| 分期 | 范围 | 状态 |
| --- | --- | --- |
| **P1 一期** | **M1 用户管理 + M2 合同智能审查 + M3 法律 AI 问答** | 设计中，尚未开工 |
| P2 二期 | 部署运维 + M4 区块链证据存证 + M5 个人中心 | 后期 |
| P3 三期 | M6 电子合同生成与签署 + M7 电子印章与签名管理 | 后期 |
| P4 四期 | 多方签署、到期提醒、分级授权、停用销毁、安全审计 | 后期 |
| P5 五期 | **微信小程序端**（移动端移植） | 后期 |
| P6 六期 | **安卓 App**（移动端移植） | 后期 |

> ⚠️ **一期是本项目的最小可交付成果**。M4–M7 的相关设计在文档中完整保留，但代码实现延后，因此文档与代码之间会存在**阶段性不一致**，这是预期状态而非缺陷。

**客户端范围**：一期只有 **Web**；**微信小程序（P5）与安卓 App（P6）**为后续移植，三端共用同一套 REST 接口、各自独立开发（不引入跨端框架）；**不做 iOS**。见 [ADR-0010](docs/adr/0010-multi-client-strategy.md)。

## 协作约定

- **仓库**：monorepo，`backend/`（FastAPI）、`frontend/`（Vue 3）、`deploy/`、`docs/` 同仓共存；Solidity 合约（`contracts/`）随 P2 区块链存证一并建立。
- **分工**：按**纵切面**（端到端业务链路）认领，而非按技术层分工。
- **流程**：功能点 → GitHub Issue → 分支 → PR → 模块**把关人**评审。把关人持 **2 票**、其他成员各 **1 票**，弃权计为反对。
- **否决边界**：代码缺陷、安全漏洞、违反契约、破坏分层依赖属**技术缺陷**，由把关人直接驳回，不进入投票；方案分歧才投票。
- **提交信息**：`<类型>(<模块>): <简述> #<issue号>`，类型为 `feat` / `fix` / `docs` / `refactor` / `test` / `chore`。提交信息是过程记录的主要载体。
- **环境**：`uv` + 项目级 `.venv`（**Python 3.14 标准构建**，`>=3.14,<3.15`），提交 `uv.lock`；克隆后 `uv sync` 即可复现，**不修改系统环境变量**。

## 凭据纪律

> ⚠️ **凭据一律不写入仓库**：服务器口令、面板密码、SSH 私钥、数据库口令与各第三方服务密钥，均存放于**仓库之外的团队内部位置**，本地开发另用 `.env` 文件（已被 `.gitignore` 忽略，模板见各目录的 `*.example`）。

**永远不要把凭据提交进版本库** —— 提交历史会永久保留，即使之后删除也仍可被检出。

主机地址、端口与登录方式**同样不入库**：本仓库可能公开，而"可登录的地址 + 端口 + 登录方式"合起来等于对外提供攻击目标。
